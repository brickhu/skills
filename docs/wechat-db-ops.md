# 有了它，你根本不需要运营后台了——db-ops，你的 AI 数据运营助理

> 开源技能 db-ops 推广｜仓库：https://github.com/brickhu/skills

---

先问一个扎心的问题：你的产品，是不是也有一个"运营后台"？

用户要改订单状态、运营要发邀请码、客服要查用户资料、活动要调配置……每次遇到这种事，你都得做一个后台页面：立项、设计、开发、测试、发版，一两个星期没了。更崩溃的是需求天天变——"这里加个按钮""那里加个筛选"，改一次发一次版。

**运营后台的本质，其实就是一个"数据库的漂亮外壳"。** 数据本来就好端端躺在数据库里，后台无非是帮你把增删改查包装得好看一点。

那如果——有一个 AI，能安全地直接操作你的数据库呢？

## db-ops：你的数据运营助理

`db-ops` 是一个开源 AI 技能包，装上之后，你的 AI 编程助手（Claude Code、Cursor、Zed 都行）就变成了你的**数据运营助理**。运营后台能干的活，它用一句话就能干：

| 运营后台要做的 | 现在直接跟 AI 说 |
|---|---|
| 开发"查用户"页面 | "看看用户 123 最近 10 笔订单" |
| 开发"改订单状态"功能 | "把订单 888 改成已发货" |
| 开发"发邀请码"工具 | "生成一个邀请码"（自动入库 + 验证） |
| 开发"活动配置"界面 | "把签到活动改成每天 3 次" |
| 写统计报表 | "统计一下本周新用户，按渠道分组" |
| 新需求来了 → 排期开发发版 | 需求变了 → 直接换一句话说 |

**不用开发、不用发版、不用等排期。** 需求今天变，今天就改，说一句话的事。

## 你一定会问：让 AI 直接动数据库，安全吗？

放心，这正是 db-ops 最花心思的地方。运营后台有的安全能力，它都有，而且更严格：

**① 权限控制（白名单）**——AI 只连你登记过的数据库，白名单外的连接一律拒绝。就像后台"谁能登录"。

**② 防连错库**——每次操作前都跟你确认连的是哪个库，哪怕只有一个库也确认。杜绝"以为是测试库，实际操作了生产库"的事故。

**③ 高危操作要"对暗号"**——删数据、改数据这类操作，AI 先给你看计划（改哪张表、影响多少行），然后要你**手打一串动态口令**才执行，比如 `confirm-DELETE-LOCAL-4`。口令里带着库名和行数，不看计划根本答不上来——防手滑，也防 AI 自作主张。这比很多后台的"二次确认"还严。

**④ 全程留痕（审计日志）**——每一次操作都记录：什么时候、连的哪个库、干了什么、影响几行。运营后台的操作日志，这里也有。

**⑤ 密钥永不露面**——密码在屏幕上永远显示为 `postgres://user:***@host`，配置文件权限锁死，想泄露都难。

**⑥ 生产库特殊照顾**——远程库和生产库的写操作，默认按最危险处理，必须经过确认流程。

一句话：**AI 负责干活，安全闸门全在你手里。**

## 适合谁？

- **独立开发者**：不再为"内部工具"消耗宝贵的开发时间，省下的时间做产品
- **小团队 / 初创公司**：没有专职开发做后台，AI 帮你兜底运营需求
- **运营 / 产品**：配合 AI 工具，自己就能查数据、调配置，不用排队等开发
- **开发者**：日常查库、改数、跑脚本，从"工具人"变"指挥人"

## 怎么装？怎么配？

**安装（二选一）：**

```sh
# 方式一：skills.sh 一键安装
npx skills add brickhu/skills

# 方式二：手动复制（任何支持 SKILL.md 的 AI 助手）
mkdir -p ~/.claude/skills
cp -r db-ops ~/.claude/skills/db-ops
```

**配置（一个文件）：**

```bash
# 项目里建 .dbops/ 目录，写 .env，一行一个数据库连接
# .dbops/.env
LOCAL=postgres://user:devpass@localhost:5432/dbname
REMOTE=postgres://user:pass@xxx.proxy.rlwy.net:50930/railway
```

支持 PostgreSQL、MySQL、SQLite。常用多步操作还能打包成快捷指令（recipes），比如"生成邀请码"，一句话触发整套流程。
